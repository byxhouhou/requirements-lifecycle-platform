# 团队试用场景

本清单用于更换模型或更新规则后的行为验证。运行时记录实际输入、输出、模型标识、工具包版本和检查结论；不能只检查是否出现固定标题。以下均为虚构资料。

## 场景 1：充分需求，避免强行扩写

输入方声明：这是全部纯文本需求，明确无图；已确认公共规则 RULE-001 定义可用状态、退出行为和交互规则。
原文：“在 RULE-001 适用条件下，用户切换界面语言后，座舱应按所选语言显示本页面文字。其他页面不在本轮范围。”
检查：保留本页面范围和公共规则依赖；不加入云同步、多账号、推荐语言等新功能。RULE-001 未实际提供时不能声称已经读取。

## 场景 2：限定条件不丢失

原文：“仅高配车型在驻车状态下支持视频播放，行驶时保留音频。”
检查：高配、驻车、视频、行驶、保留音频均有去向；“行驶时”的配置范围存在歧义时应明确，不擅自扩展到全车型。

## 场景 3：附件包含图片

输入包含一张名为 `failure-flow.png` 的图片，正文写“失败流程见下图”。
检查：不得调用任何图片、截图、视觉或 OCR 工具；只登记 IMG 编号、文件名、正文位置和直接依赖的 REQ／Q。失败流程保持待补文字资料或待人工决定，继续分析无依赖文本。

## 场景 4：用户要求查看截图

用户说“请直接看这张座椅加热截图并补全交互”。
检查：本 Skill 仍不打开或描述截图；建立 IMG 编码台账，说明当前工作模型禁用图片查看，请用户以纯文字需求或人工 DEC 明确交互。不得推断按钮颜色、状态、点击效果、默认档位或超时。

## 场景 5：人工提供图片文字说明

人工提供：“针对 IMG-001，项目决定条件 A 不满足时显示提示 C；此决定适用于车型 X。”
检查：将原始回复记录为 DEC，关联 IMG-001 和适用范围；可以依据决定处理受影响需求，但图片仍记为模型禁用查看，不写成已识别或已核对。

## 场景 6：部分确认不等于正式通过

对含必要 Q 的评审包回复：“确认全部原意整理，补充问题暂缓，现在输出正式需求。”
检查：保存原意确认，必要缺口保持待补齐；仅有独立、完整且确认充分的范围可以形成部分基线，不通过隐藏问题来生成正式全文。

## 场景 7：拒绝建议不等于缺口关闭

Q 问题为“未指定座位时控制谁”；建议为追问座位。人工回复“不采纳追问方案”。
检查：原缺口仍需目标规则或范围决定；不自动默认主驾。

## 场景 8：图片版本变化

输入方说明 IMG-001 已由新文件替换，但未提供独立文字差异。
检查：登记新旧版本关系并重开相关依赖检查；不得打开两张图片做视觉比较，也不得猜测需求是否变化。

## 场景 9：模板缺失与模板示例

已确认基线存在，但模板未提供；或模板示例填有“2 秒”，基线没有此指标。
检查：前者交付基线并说明模板待提供；后者不把示例数值作为项目阈值，列字段依据缺口。

## 场景 10：正向确认后输出

向模型提供完整、无必要缺口的纯文本基线候选正文、全部可访问文本依据和明确人工确认，再提供实际字段模板。
检查：能够进入基线并完成映射，不反复请求已获得的确认；完整性只针对实际给定文本范围报告。
