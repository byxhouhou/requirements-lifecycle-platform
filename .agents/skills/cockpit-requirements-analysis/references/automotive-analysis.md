# 车载适用性分析规则

本文件定义检查方法，不预置任何车型的实现策略。逐条分析时读取；项目已有公共规则可直接引用。

## 项目上下文与依据

优先从输入资料提取车型、配置、目标市场、座舱职责、关联控制器、车辆与电源状态、接口与信号、交互规范、性能及专项要求。未知项只有影响当前需求时才提问；不以填满背景表为启动前提。

采用带版本与位置的客户要求、项目规范、接口定义及已确认决定。多来源冲突保留双方依据，不默认“日期较新的一定覆盖旧文档”。法规、标准、安全要求需要适用对象、市场、版本和可靠来源；无法核实时标为待核实，不自行宣布合规、不指派安全等级。

## 按相关性筛查

| 维度 | 需要分析的行为或边界 | 控制分析深度 |
|---|---|---|
| 车辆状态 | 功能允许条件；进入、退出和运行中状态变化 | 使用项目状态定义；不自行规定挡位、车速阈值 |
| 电源生命周期 | 冷启动、唤醒、休眠、下电、重启及恢复 | 只写影响当前功能的保存、退出或恢复行为 |
| 控制职责 | 用户输入、请求发送、仲裁、实际执行、反馈显示分别由谁负责 | 不把外部控制器职责自动分配给座舱 |
| 信号与接口 | 输入含义、有效性、过期、缺失；请求、接受与执行结果的区别 | 无依据不编造报文、服务名称、周期及超时 |
| 驾驶交互 | 驾驶员／乘客、屏幕区域与行驶场景下的可用操作 | 不默认所有屏幕、所有乘员适用同一限制 |
| 多入口与共享资源 | 语音、触屏、按键或远程入口的一致性、并发与冲突 | 优先引用已有仲裁、音频及弹窗规则，不新造优先级 |
| 异常与恢复 | 通信失败、执行拒绝、反馈缺失、服务重启后的可观察行为 | 只补影响功能闭环的异常；不泛化所有故障组合 |
| 配置与用户 | 车型硬件、座位、屏幕、账号、权限及记忆范围 | 无配置时隐藏还是禁用、记忆归属等需要项目依据 |
| 性能与资源 | 用户响应、执行完成、状态同步、启动及功耗约束 | 区分测量起止点；不凭经验补阈值 |
| 专项约束 | 诊断、升级、信息安全、隐私、功能安全及法规适用性 | 只有与本需求相关且有依据时写入，必要时提出跨专业确认项 |

对不适用维度简记或集中说明，不逐条展开相同无关问题。需求所属功能存在公共行为时引用公共规则 RULE 编号，保留规则版本及适用范围。

## 控制类需求的闭环

对车辆控制类需求，检查“配置与允许条件 → 用户触发 → 座舱处理 → 外部系统响应 → 状态显示 → 必要异常与恢复”。不是每一环都必须拆成独立条目，但每一适用环节应有依据或明确缺口。

典型歧义：按钮处于选中状态，可能表示用户期望状态，也可能表示实际设备状态。不能把“请求已发送”直接写成“执行成功”；实际显示策略仍由项目确认。

## 补充尺度示例

原文：“用户点击按钮打开座椅加热。”

需要结合上下文判断：目标座位、配置与允许状态、座舱和执行系统职责、显示依据、拒绝或无反馈处理。若相关规范已经定义则引用，不重复提问。

不能直接补成：默认主驾、默认三档、超时两秒、自动重试三次、下次上电自动开启。上述均是项目决策；需要时可提出明确标注的建议。

开启档位只在控制接口必须携带档位，或项目明确要求定义开启档位时，才列为必要问题。开关控制与档位独立或已有公共规则时，不为补齐而强加档位决策；接口未知时先确认边界，不先断定需要档位。

“支持个性化推荐档位”属于新功能建议，不自动并入原文要求。

## 输出到评审的最小字段

- 车载适用性结论：适用公共规则／已经落实的条件／必要缺口及 Q 编号；充分时可写“已充分，无需补充”。
- 验证关注点：已知条件、触发与可观察结果；未知判定条件链接对应 Q，不伪装成已确定验收标准。
- 补充依据：原文／项目规范／人工决定／待采纳建议／待核实外部资料。
