# 车载智能座舱需求分析 Skill · 团队使用说明

版本：**0.4.0**。定位：团队试用版。面向系统需求工程师和纯文本工作模型。当前包包含需求工作流、车载分析规则、图片编码策略及评审表单；项目正式输出模板由项目组提供。

## 本版本的图片约束

使用本 Skill 时，模型不得打开、预览、识别、OCR、描述、分类或推断图片，也不得调用图片工具、视觉模型、截图接口或外部图片服务。即使运行环境提供视觉能力，该限制也不解除。

图片只分配 `IMG-xxx` 编码并登记位置、版本、文件名、正文引用和需求影响。“编码”是追溯编号，不是 Base64 或二进制转换。依赖图片语义的需求保持待补文字资料或待人工决定；无依赖的文本需求继续处理。

## 五步开始

1. 系统需求工程师登记客户资料、版本、文本范围和确认责任人，使用 [项目输入表](assets/project-intake.md) 填写已知信息。
2. 输入含图片、扫描件或截图时，不让模型打开它们。根据文档结构、正文引用或输入方清单填写 [图片编码登记表](assets/image-register.md)。未知数量或位置如实写未知。
3. 调用 Skill，要求先输出 [需求评审包](assets/review-pack.md)。模型只分析可访问文本，并把图片依赖登记为 Q 或范围缺口。
4. 人工按 REVIEW 版本、REQ／Q／IMG 编号回复。图片相关行为必须通过独立文字 SRC 或明确 DEC 提供，不能用“请看图”代替。
5. 只有完整正文获得确认且必要缺口闭环的条目进入基线；提供项目正式模板后，再映射确认基线并做双向核对。

具体入口条件、责任与完成标准见 [SOP](SOP.md)。

## 使用方式

### 在 Codex 项目中使用

本目录按项目 Skill 结构组织：`.agents/skills/cockpit-requirements-analysis/`。团队应复制完整目录，避免只复制 SKILL.md 而漏掉 references 和 assets。

在支持技能选择的界面选择“车载智能座舱需求分析”。Codex CLI／IDE 可用 `$cockpit-requirements-analysis` 显式调用。默认保留自动匹配；更新未显示时可重启客户端。同名技能不会自动合并，应避免多份同时被发现。[官方技能文档](https://learn.chatgpt.com/docs/build-skills)

无论客户端是否支持图片，都按本 Skill 的禁用规则执行。不要在启动语句中要求模型查看附件图、截图、扫描页或做 OCR。

### 在只能接收单个文本文件的平台中使用

导入 [SKILL_FULL.txt](portable/SKILL_FULL.txt)。其中已内嵌核心规则、分析参考和空白表单，无需访问本机相对路径。

客户文本原文、项目规范、图片编码台账和历史人工决定作为任务资料另行提供。不要附加图片让模型尝试读取；图片文件只在团队原始资料中保存，其台账用 IMG 编号关联。

上下文不足时按功能或章节分批，每批交接文本范围、全局编号、图片编码范围、公共规则、未决问题和确认记录。不能只保留摘要后声称全部覆盖。

无需模型 API Key、联网服务或 Python 即可日常执行文本工作流。Python 仅用于维护人员重新生成分发包。

## 可直接复制的启动语句

### 新需求分析

```text
请使用 $cockpit-requirements-analysis。
项目：填写项目或功能名称。
本轮范围：填写资料名称、版本及章节范围。
原始文本资料与项目规范：附在本次任务中。
图片情况：明确无图／已提供 IMG 编码台账／有图片但范围未知。
禁止打开、识别、OCR 或调用任何图片，只做 IMG 编码登记。
本轮先输出待人工确认版：需求评审表、待确认问题表、来源覆盖附表。
逐条分析车载适用性，必要补充与原文分开；充分的需求无需扩写。
正式模板尚未提供时，先完成评审包。
```

纯文本平台可将第一句替换为“请按已导入的 SKILL_FULL.txt 执行”。

### 提交人工意见

```text
针对 REVIEW-003：
确认 REQ-001、REQ-002 的原意整理。
Q-001 采纳所展示的方案 A。
IMG-001 相关行为按 DEC-004 的纯文字决定处理，不要求模型查看图片。
REQ-003 暂缓，其他未提及内容保持原状态。
请合并上述决定，展示完整需求及差异，判断哪些条目可入基线。
```

明确决定已覆盖最终含义时无需再次确认相同内容。仅确认原意、含糊意见或缺失被引用资料，均不能自动变成正式需求通过。

### 根据基线输出

```text
使用 BASELINE-002 和本次提供的正式模板 v1。
仅输出基线明确纳入的范围，保留模板字段映射。
缺字段依据或已确认内容无承载位置时，列出具体缺口。
输出后分别检查文本读取完整性、图片编码完整性、信息去向完整性和本版本落实完整性。
```

## 团队协作约定

| 角色（可兼任） | 负责内容 |
|---|---|
| 系统需求工程师 | 组织文本输入、执行分析、提出必要问题、合并决定、维护追溯 |
| 资料登记人 | 根据文档结构或输入方清单维护 DOC／IMG 编码和位置，不要求模型读取图片 |
| 确认责任人 | 确认原意、策略、范围和冲突；用独立文字提供图片相关行为决定 |
| 交付负责人 | 核对基线、模板和范围，保存交付记录 |
| Skill 维护人 | 更新通用规则、试用样例及版本，生成分发包 |

模型负责文本分析和记录，人负责项目决策。不得把“已建立 IMG 编码”记成“图片已读取”或“全部需求已通过”。

建议每个项目独立保存 `inputs/`、`image-registers/`、`reviews/`、`baselines/`、`outputs/`。这是团队存档建议，不要求改动客户模板或工具目录。

## 四个容易混淆的结论

- **图片已编码**：已记录 IMG 编号和可用元数据；图片内容仍未查看。
- **确认原意**：文本整理没有曲解客户。
- **可入基线**：完整正文及必要条件已明确且确认，图片语义不再构成未定依赖。
- **完整覆盖**：只针对明确的文本范围报告；含图片的资料另报编码范围和模型未查看声明。

基线可以只包含明确确认的部分，但须记录范围及依赖；部分基线不能替代原始文本全量完整性检查。完整状态规则见 [评审和基线规则](references/review-and-baseline.md)。

## 维护与重新打包

维护源文件，不直接手改合并版。工具包版本记录在 VERSION、SKILL.md、README、SOP 及表单中；升级时保持一致。工具包版本与客户文档、评审、基线、模板版本各自独立。

在本 Skill 目录执行（Python 3.10+，脚本仅使用标准库）：

```text
python scripts/package_skill.py --output-dir dist
```

脚本会校验本地链接、文件清单和版本，重新生成 `portable/SKILL_FULL.txt`，并生成版本 ZIP 与 SHA-256 清单。包中不包含客户项目资料，也不会上传文件或修改客户端配置。

更新后按 [试用场景](examples/smoke-cases.md) 验证，尤其检查模型在存在图片附件时不会发起任何图片调用。结构检查通过只证明封装可读；分析质量须通过具体文本样例和团队试用验证。

## 当前交付边界

当前正式输出模板尚未提供，包内提供评审与基线表单以及模板映射机制。最终模板适配将在收到项目模板后完成。

不同模型的指令遵循、上下文容量和文件读取能力存在差异。首次使用或更换模型时运行试用场景，记录模型、工具包版本及实际结果。
