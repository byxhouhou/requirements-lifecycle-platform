# 车载智能座舱需求分析 Skill · 团队使用说明

版本：**0.3.0**。定位：团队试用版。面向系统需求工程师，支持纯文本大模型。当前包已包含工作流、车载分析规则、图片策略及评审表单；项目正式输出模板由项目组后续提供。

## 团队拿到什么

| 文件 | 用途 | 主要使用者 |
|---|---|---|
| [SKILL.md](SKILL.md) | 模型执行入口和核心规则 | 模型／Skill 维护人 |
| [SOP.md](SOP.md) | 从接收客户资料到输出归档的操作步骤 | 项目团队 |
| [项目输入表](assets/project-intake.md) | 登记范围、来源版本、角色和模型能力 | 系统需求工程师 |
| [图片转写交接表](assets/image-transcription.md) | 让能看图的一方交付文字和关系 | 资料处理人／图片核对人 |
| [需求评审包](assets/review-pack.md) | 需求表、问题表、覆盖表和人工决定记录 | 分析人／确认人 |
| [基线与映射表](assets/baseline-and-template-mapping.md) | 保存完整确认正文并映射正式模板 | 分析人／交付负责人 |
| [评审示例](examples/review-example.md) | 演示评审与确认的区别 | 首次使用者 |
| [试用场景](examples/smoke-cases.md) | 更换模型或更新规则后的行为检查 | Skill 维护人 |
| [纯文本合并版](portable/SKILL_FULL.txt) | 一次导入全部模型规则与空白表单 | 无关联文件读取能力的平台 |

本包是需求分析工作流，不提供自动 OCR 服务，不代替工程决策或项目合规判定。表单中的空白和“待填写”供实际项目填入；示例均为虚构，不作为真实项目需求或确认依据。

## 五步开始

1. 由系统需求工程师登记客户资料、版本与范围，并指定本轮确认责任人。使用 [项目输入表](assets/project-intake.md)，已有资料能回答的内容直接引用。
2. 含图片时由可查看原图的人员或工具填写 [图片转写交接表](assets/image-transcription.md)。只有 OCR 文字而没有结构关系时，仍标记未完整核对。
3. 调用 Skill，要求先输出 [需求评审包](assets/review-pack.md)。先看需求表和问题表，必要时展开来源与条目详情。
4. 人工按 REVIEW 版本、REQ／Q 编号回复。模型合并决定，只有完整正文获得确认且必要缺口闭环的条目进入基线。
5. 提供项目正式模板，由模型映射确认基线并做双向核对。模板未提供时停留在评审或基线交付，仍可完成前四步。

具体入口条件、责任与完成标准见 [SOP](SOP.md)。

## 使用方式

### 在 Codex 项目中使用

本目录按项目 Skill 结构组织：`.agents/skills/cockpit-requirements-analysis/`。团队将完整目录放入自己的项目相同位置，并通过版本控制或受控文件包共享。不要只复制 SKILL.md 而漏掉 references 和 assets。

在支持技能选择的界面选择“车载智能座舱需求分析”。Codex CLI／IDE 可用 `$cockpit-requirements-analysis` 显式调用。默认保留自动匹配。当前官方文档说明项目 Skill 从 `.agents/skills` 发现，更新未显示时可重启客户端；同名技能不会自动合并，应避免多份同时被发现。[官方技能文档](https://learn.chatgpt.com/docs/build-skills)

本仓库的 `skill-drafts/` 保留早期草稿；团队维护以本目录为准。本包完成文件封装不等于已在每位成员的客户端验证可见性。

### 在不能处理图片的模型中使用

- 平台能读取多个文本文件：提供 SKILL.md、references 和 assets，并确认关联文件实际可访问。
- 平台只能接收一段指令或一个文件：导入 [SKILL_FULL.txt](portable/SKILL_FULL.txt)。其中已内嵌核心规则、所有分析参考和空白表单，无需访问本机路径。
- 依平台实际能力将合并版放入可持续生效的指令／知识上下文；不支持持久指令时，在任务开始明确要求按该文件执行。
- 客户原文、图片转写、项目规范和历史人工决定作为本次任务资料另行提供。
- 合并文本不赋予识图能力。视觉信息须先转写；不要给纯文本模型图片地址后假定它已经看过。
- 上下文不足时按功能／章节分批，每批交接原文范围、全局编号、公共规则、未决问题和确认记录。不能仅保留摘要后声称全部覆盖。

无需模型 API Key、联网服务或 Python 即可日常执行文本工作流。Python 仅用于维护人员重新生成分发包。

## 可直接复制的启动语句

### 新需求分析

```text
请使用 $cockpit-requirements-analysis。
项目：填写项目或功能名称。
本轮范围：填写资料名称、版本及章节范围。
原始资料与项目规范：附在本次任务中。
图片情况：明确无图／已附转写与核对记录／尚有未处理图片。
本轮先输出待人工确认版：需求评审表、待确认问题表、来源覆盖附表。
逐条分析车载适用性，必要补充与原文分开；充分的需求无需扩写。
正式模板尚未提供时，先完成评审包。
```

纯文本平台可将第一句替换为“请按已导入的 SKILL_FULL.txt 执行”。

### 提交人工意见

```text
针对 REVIEW-003：
确认 REQ-001、REQ-002 的原意整理。
Q-001 采纳所展示的方案 A。
Q-002 按本次提供的接口规范 v2 第 4 节处理。
REQ-003 暂缓，其他未提及内容保持原状态。
请合并上述决定，展示完整需求及差异，判断哪些条目可入基线。
```

明确决定已覆盖最终含义时无需再次确认相同内容。仅确认原意、含糊意见或缺失被引用资料，均不能自动变成正式需求通过。

### 根据基线输出

```text
使用 BASELINE-002 和本次提供的正式模板 v1。
仅输出基线明确纳入的范围，保留模板字段映射。
缺字段依据或已确认内容无承载位置时，列出具体缺口。
输出后分别检查读取完整性、信息去向完整性和本版本落实完整性。
```

## 团队协作约定

| 角色（可兼任） | 负责内容 |
|---|---|
| 系统需求工程师 | 组织输入、执行分析、提出必要问题、合并决定、维护追溯 |
| 资料／图片处理人 | 核对原文范围，转写与检查图片，不替项目决定行为 |
| 确认责任人 | 根据团队职责确认原意、策略、范围与冲突；必要时协调客户或相关专业 |
| 交付负责人 | 核对基线、模板和范围，保存交付记录 |
| Skill 维护人 | 更新通用规则、试用样例及版本，生成分发包 |

模型负责辅助分析和记录，人负责项目决策。不要把“一位人员核对图片”记成“全部需求已通过”，也不额外要求每个角色对每条需求重复审批。

建议每个实际项目独立保存 `inputs/`、`transcriptions/`、`reviews/`、`baselines/`、`outputs/`。这是团队存档建议，不要求改动客户模板或工具目录。

## 三个容易混淆的结论

- **确认原意**：整理没有曲解客户。
- **可入基线**：完整正文及必要条件已明确且确认，依赖不再阻碍。
- **完整覆盖**：范围明确，原文和图片全部核对且信息逐项有去向。

基线可以只包含明确确认的部分，但须记录范围及依赖；部分基线通过不能替代原始资料全量完整性检查。完整状态规则见 [评审和基线规则](references/review-and-baseline.md)。

## 维护与重新打包

维护源文件，不直接手改合并版。工具包版本记录在 VERSION、SKILL.md、README、SOP 及表单中；升级时保持一致。工具包版本与客户文档、评审、基线、模板版本各自独立。

在本 Skill 目录执行（Python 3.10+，脚本仅使用标准库）：

```text
python scripts/package_skill.py --output-dir dist
```

脚本会校验本地链接、文件清单和版本，重新生成 `portable/SKILL_FULL.txt`，并生成版本 ZIP 与 SHA-256 清单。包中不包含客户项目资料，也不会上传文件或修改其他客户端配置。

更新后按 [试用场景](examples/smoke-cases.md) 验证。结构检查通过只证明封装可读；分析质量须通过具体样例和团队试用验证。适配实际正式模板后，应再验证字段映射、承载位置与格式。
